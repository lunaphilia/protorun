# Protorun 設計決定書 (Design Decisions)

本ドキュメントは、Protorun言語のMVP（Minimum Viable Product）仕様策定において確定された主要な設計決定を記録する。

## 1. スコープ: MVP仕様完成
- **決定内容**: 言語の最小限の実用的なサブセットを定義し、仕様上の全ギャップを解消する。
- **根拠**: 曖昧な仕様や未定義の機能を排除し、実装者が迷わずにパーサーやインタープリタを構築できるようにするため。
- **代替案**: フル機能の仕様策定を継続する。
- **トレードオフ**: 実装の容易さを優先し、一部の高度な機能（所有権等）を後回しにする。
- **構文例**: N/A

## 2. ループ設計: Effektスタイル
- **決定内容**: `while`, `for`, `loop` を組み込み構文とし、`break` と `continue` は代数的効果として扱う。
- **根拠**: 制御フローの柔軟性を保ちつつ、代数的効果の強力な表現力を活かす。Effekt言語の実績に基づく。
- **代替案**: Kokaのようにループ自体をライブラリ関数（thunk）として実装する。
- **トレードオフ**: ループ自体は組み込みのため最適化しやすいが、制御フロー操作には効果ハンドラが必要になる。
- **構文例**:
  ```protorun
  with break {
    loop {
      if condition { break.break() }
    }
  }
  ```

## 3. 文法正規化: EBNFを正規仕様
- **決定内容**: 基本的にEBNFを正とする。ただし、明白なバグ（戻り値型 `:` vs `->` 等）は散文や一般的慣習に合わせてEBNFを修正する。
- **根拠**: 仕様の一貫性を保つため。
- **代替案**: 散文（ドキュメントのコード例）を正とする。
- **トレードオフ**: 既存のドキュメントのサンプルコードを一部修正する必要がある。
- **構文例**: N/A

## 4. ジェネリクス曖昧性: Scala方式
- **決定内容**: ジェネリクスには `[T]` を使用し、インデックスアクセスは `list.get(0)` のようなトレイトメソッドで行う。
- **根拠**: `<T>` は比較演算子との曖昧性が生じやすく、パーサーの複雑化を避けるため。
- **代替案**: Rust/C++のように `<T>` を採用し、ターボフィッシュ `::<>` を導入する。
- **トレードオフ**: インデックスに `[]` を使えないが、型パラメータの視認性が向上する。
- **構文例**:
  ```protorun
  fn identity[T](x: T) -> T { x }
  let val = list.get(0)
  ```

## 5. エントリポイント: トップレベル式
- **決定内容**: ファイルのトップレベルに記述された式が上から順に実行されるスクリプト形式を採用する。
- **根拠**: 小規模なスクリプトや実験的なコードを素早く書けるようにするため。
- **代替案**: 明示的な `fn main()` 関数を必須とする。
- **トレードオフ**: 巨大なプロジェクトでの構造化が難しくなる可能性があるが、MVPのシンプルさを優先。
- **構文例**:
  ```protorun
  println("Hello, World!")
  let x = 10
  ```

## 6. `?` 演算子: MVP仕様から除外
- **決定内容**: エラー伝播の `?` 演算子はMVPには含めない。
- **根拠**: `Result` 型とパターンマッチング、または代数的効果によるエラーハンドリングで代替可能であり、構文の複雑さを抑えるため。
- **代替案**: Rustスタイルの `?` を導入する。
- **トレードオフ**: エラーハンドリングがやや冗長になるが、言語の核となる概念（効果）の利用を促す。
- **構文例**:
  ```protorun
  match perform_io() {
    Ok(val) -> val,
    Err(e) -> return Err(e)
  }
  ```

## 7. 所有権システム: MVP仕様から除外
- **決定内容**: 所有権と借用（ch7）の全仕様を将来フェーズに延期し、MVPはGC（ガベージコレクション）ベースの言語とする。
- **根拠**: 代数的効果（特に継続）と線形型の相互作用は設計上の難易度が高く、MVPのリリースを遅らせる要因となるため。
- **代替案**: 簡略化した所有権システムを導入する。
- **トレードオフ**: メモリ安全性の保証がランタイムに依存するが、開発効率と学習コストが大幅に改善される。
- **構文例**: N/A

## 8. 文字列補間: Python風 `f"...{expr}..."`
- **決定内容**: `f` プレフィックスと `{}` を使用した文字列補間を採用する。
- **根拠**: 実装が比較的容易で、多くの開発者にとって馴染み深い構文であるため。
- **代替案**: Scala風の `s"..."` や、Ruby風の `"#{...}"`。
- **トレードオフ**: 文字列リテラルにプレフィックスが必要になるが、エスケープの混乱が少ない。
- **構文例**:
  ```protorun
  let name = "Alice"
  println(f"Hello, {name}!")
  ```

## 9. 数値型: サイズ付き完全サポート
- **決定内容**: `i8`〜`i128`, `u8`〜`u128`, `f32`, `f64` をサポートする。`Int` は `i64`, `Float` は `f64` のエイリアスとする。
- **根拠**: システムプログラミングや低レイヤ操作への将来的な対応を見据え、型安全な数値操作を提供するため。
- **代替案**: `Int` と `Float` のみを基本型とする。
- **トレードオフ**: 型の数が増えるが、メモリレイアウトの制御が明確になる。
- **構文例**:
  ```protorun
  let small: u8 = 255
  let big: i128 = 1000000000000000000000
  ```

## 10. メソッド/インデックス: トレイトメソッド
- **決定内容**: メソッド呼び出し `x.f(y)` は、まずトレイトメソッドとして解決し、次に関数 `f(x, y)` として解決する（UFCS）。インデックスも `get` トレイトメソッドとする。
- **根拠**: 拡張性と一貫性を保ちつつ、オブジェクト指向的な記法を許可するため。
- **代替案**: 厳密なUFCSのみ、または厳密なクラスベースのメソッド。
- **トレードオフ**: 名前衝突の解決ルールがやや複雑になる。
- **構文例**:
  ```protorun
  list.get(0)
  // は以下と同等（解決順による）
  get(list, 0)
  ```

## 11. 標準ライブラリ: 最小prelude
- **決定内容**: `Option`, `Result`, `List`, `Map`, `Set`, `String`, `Iterator`, `Show`, `Eq`, `Ord`, 数値トレイト, `Console` 効果を最小構成とする。
- **根拠**: 実用的なプログラムを書くために最低限必要なデータ構造とインターフェースを定義する。
- **代替案**: より広範なライブラリ、または全くなし。
- **トレードオフ**: 標準ライブラリの設計負担があるが、エコシステムの基礎となる。
- **構文例**: N/A

## 12. リストパターン/スプレッド: MVP除外
- **決定内容**: リストのパターンマッチングやスプレッド演算子（`...`）をMVPから除外する。
- **根拠**: 文法定義と実装を簡素化するため。
- **代替案**: 可変長引数や完全なリストパターンを導入する。
- **トレードオフ**: リスト操作がメソッドベースになり、パターンマッチがやや制限される。
- **構文例**:
  ```protorun
  // match [1, 2, 3] { [x, ...xs] -> ... } は不可
  let list = [1, 2, 3]
  let head = list.head()
  let tail = list.tail()
  ```

## 13. 演算子オーバーロード: MVP組み込みのみ
- **決定内容**: ユーザー定義の演算子オーバーロードをMVPではサポートせず、組み込み型に対してのみ機能させる。
- **根拠**: セマンティクスの複雑化とコンパイル時の解決コストを抑えるため。
- **代替案**: トレイトを用いた完全な演算子オーバーロード。
- **トレードオフ**: ユーザー定義型の利便性は下がるが、言語コアが安定する。
- **構文例**: N/A

## 14. 追加要望: 特になし
- **決定内容**: 現時点で新たな機能追加は行わない。
- **根拠**: フォーカスをMVPの完成に絞るため。
- **代替案**: N/A
- **トレードオフ**: N/A

## 15. 関数戻り値型: `->` に統一
- **決定内容**: EBNFで `:` となっていた戻り値型の指定を、散文コードに合わせて `->` に統一する。
- **根拠**: 他のモダンな言語（Rust, Python, Swift等）との親和性が高く、視認性も良いため。
- **代替案**: `:` を維持する（Scala, Kotlinスタイル）。
- **トレードオフ**: 特になし。
- **構文例**:
  ```protorun
  fn add(a: Int, b: Int) -> Int { a + b }
  ```

## 16. 可変フィールド: `mut` に統一
- **決定内容**: `let mutable` や `mut val` などの混在を廃止し、フィールドや変数宣言に `mut` キーワードを使用する形式に統一する。
- **根拠**: 記述の簡潔さと一貫性のため。
- **代替案**: `var` / `val` の使い分け。
- **トレードオフ**: 特になし。
- **構文例**:
  ```protorun
  struct Point {
    mut x: Int,
    mut y: Int,
  }
  let mut counter = 0
  ```

## 17. トップレベル効果: 明示的with必須
- **決定内容**: 全ての効果（Effect）は、必ず `with` ハンドラ内で実行されなければならない。暗黙的なデフォルトハンドラは存在しない。
- **根拠**: 意図しない副作用の発生を防ぎ、効果の追跡を厳格にするため。
- **代替案**: `Console` 等の基本的な効果にデフォルトハンドラを用意する。
- **トレードオフ**: `println` などの単純な操作にも `with console` が必要になり、ボイラープレートが増える可能性がある。
- **構文例**:
  ```protorun
  with console {
    println("Hello")
  }
  ```

## MVPスコープ

### IN (含める機能)
- 代数的効果（Effect, perform, with/handle）
- 組み込みループ（while, for, loop）+ 効果ベースのbreak/continue
- トレイト（Trait）と構造体（Struct）
- パターンマッチング（match）
- ジェネリクス（[T] 形式）
- 基本的な数値型、文字列、リスト、マップ、セットのリテラル
- 文字列補間（f"..."）
- モジュールシステム（module, import）
- 標準ライブラリの最小セット（prelude）

### OUT / 延期 (除外する機能)
- 所有権システムと借用チェッカ（GCベースに変更）
- エラー伝播演算子（?）
- ユーザー定義の演算子オーバーロード
- リストのスプレッド演算子および複雑なリストパターン
- 暗黙的な効果ハンドラ
- 非同期構文（async/await - 代数的効果で実現可能なため）
